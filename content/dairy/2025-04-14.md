**一、毕业设计（论文）主要研究内容、进展情况及取得成果**

**1.1 系统架构设计：基于 KServe 的无服务器推理服务增强与定制**

1.1.1 **架构理解与适配**  
本研究**基于业界领先的无服务器推理框架 KServe** 及其依赖的 Kubernetes 和 Knative 生态。首先，深入研究了 KServe 的核心设计理念，特别是其 InferenceService 自定义资源（CRD）定义、模型服务的生命周期管理（如模型加载、更新机制）、请求路由和服务网格（如 Istio/Kourier）的集成方式，以及其与 Kubernetes 资源调度（如 HPA、节点亲和性）的协同逻辑。在此基础上，**我们遵循 KServe 的设计范式构建了一个推理服务实例**，并**特别关注在单节点 Pod 层面**的模型推理服务部署与优化，旨在提升无服务器环境下的资源效率和响应性能，同时确保服务的稳定性和可观测性。

1.1.2 **多模型服务支持与 KServe 模式借鉴**  
系统设计**借鉴了 KServe 对多模型推理服务的支持方式及其边车（Sidecar）设计模式**。支持部署常见的机器学习模型（如 Scikit-learn、PyTorch 服务实例），并**采用了与 KServe 兼容或类似的标准化模型输入/输出接口**（例如，通过 RESTful API 使用 JSON/ProtoBuf 进行序列化）以及模块化的预/后处理逻辑。特别地，**在 Pod 内引入了定制化的 Agent 边车**，用于模型文件的拉取与本地缓存，**这与 KServe 的 Model Agent 理念一致**，旨在减少模型重复加载开销，优化冷启动场景下的响应速度。

**1.2 节点单 Pod 批处理（Batching）优化策略设计与实现**

1.2.1 **批处理优化场景与目标定义**  
针对部署在**单个 Pod 内**的模型推理服务，研究其批处理（Batching）优化策略。核心目标设定为：  
* **目标一（性能优先）：** 在典型负载下，通过动态调整批处理参数，寻求**推理延迟（Latency）与系统吞吐量（Throughput）之间的最佳平衡点**。  
* **目标二（SLO 约束）：** 在满足预定义的服务级别目标（SLO，例如 P99 延迟需低于特定阈值）的前提下，**最大化 Pod 的推理吞吐量**。  
为此，需要分析批处理的关键参数（批大小 batch_size、批处理最大等待时间 timeout）与系统性能指标（吞吐量、时延）之间的相互影响关系，并考虑请求到达率、模型单次推理时间等动态因素。**本研究旨在探索有效的动态批处理决策机制，而非构建复杂的数学优化模型。** (这里明确降低了对数学模型复杂度的预期)

1.2.2 **动态批处理机制设计与初步实现**  
在 Pod 内**开发并集成了一个轻量级的批处理 Agent**，其核心功能包括：  
* **请求队列管理：** 实现了一个异步请求队列（例如基于 FIFO 策略），用于缓存 Pod 接收到的待处理推理请求。批处理操作的触发机制基于**时间窗口**（例如，等待达到设定的 timeout，如 50ms）和/或**批大小阈值**（例如，队列中积累的请求数达到设定的 batch_size，如 32 个）。  
* **动态参数调整探索：** Agent 负责**采集**批处理过程中的相关性能指标（如实际批大小、处理延迟、队列等待时间）以及 Pod 的运行时信息（可能包括 CPU/内存利用率、请求到达速率估计等）。基于这些信息，**尝试采用启发式规则或简单的反馈控制逻辑**，动态调整批处理的 batch_size 和 timeout 参数，以趋近预设的优化目标（平衡延迟/吞吐量 或 SLO 约束下的吞吐量最大化）。

**目前的进展情况和成果：**

**已完成部分**

- **基于 KServe 模式的推理服务架构部署与验证**
    - **理解与实践 KServe 架构：** 深入学习了 KServe 的核心组件和工作流程，**并在 Kubernetes (通过 WSL Kind 集群) 与 Knative 环境中，成功部署和运行了一个遵循其模式的简化推理服务实例**。
    - **推理运行时容器化：** 使用 FastAPI 构建了支持 /infer 通用接口的推理运行时容器镜像。针对 Scikit-learn 和 PyTorch 框架，分别创建了运行时实现，支持动态加载模型文件。
    - **自定义资源（CRD）与控制器实践：** **学习并实践了 KServe InferenceService CRD 的使用方式**。**基于 Kubebuilder 工具，开发了一个简化的控制器**，该控制器能够监听自定义资源（例如，一个名为 SimpleInferenceService 的 CRD），并根据其定义自动创建或管理底层的 Knative Service 及相关 Kubernetes 资源（如 Deployment, Service）。**实践了控制器中的“调和”（Reconcile）逻辑**，以同步期望状态与实际状态。
    - **Webhook 与边车注入实践：** **理解并实践了 Kubernetes 的 Mutating/Validating Webhook 机制**。创建了 Webhook 配置，用于：1) **注入默认值**（如为 Pod 设置默认资源请求/限制）；2) **动态注入自定义的 Agent 边车容器**（包括模型拉取 Agent 和批处理 Agent），并通过 volumeMounts 实现了模型文件在主容器与边车间的共享（挂载至如 /mnt/models）。
    - **模型拉取 Agent 初步实现：** 开发了一个轻量级 Go 语言 Agent，能够根据 CRD 中指定的模型 URI（例如，S3 路径或 HTTP URL），将模型文件下载到 Pod 内的共享卷。
    - **批处理 Agent 基础框架搭建：** 使用 Go 语言初始化了批处理 Agent 的基本结构，包括请求接收端点、内部请求队列（缓冲区）和批处理任务的触发逻辑框架，为后续实现动态策略奠定了基础。
    - **端到端部署流程验证：** 在 WSL Kind 集群中，通过 kubectl apply -f <crd-instance.yaml> 成功触发了从 CRD 创建到 Knative Service 部署、边车注入、模型拉取的完整流程，验证了服务能够启动并准备接收请求。
- **实验体系初步设计**
    - **负载场景定义：** 确定了用于测试的基础负载类型，包括使用简单的 Scikit-learn 和 PyTorch 模型进行的合成请求，以及**模拟**类似微软 Azure Functions 调用模式的请求流。
    - **测试工具与数据准备：** 基于 Python 开发了基础的压力测试脚本，用于向部署的服务发送推理请求。完成了用于实验追踪（Trace）的指标选取考量和初步的数据清洗脚本准备工作，为后续系统性能评估奠定基础。

**正在进行部分**
1. **系统可观测性体系构建（进行中，完成度 70%）**
    - **基于 Prometheus 的指标采集：** 正在配置和部署 Prometheus 及相关 Exporter，以收集三个层面的指标：
        - **基础设施层 (Knative/K8s):** 重点关注 Knative Queue Proxy 指标（如 revision_app_request_latencies, revision_app_request_count）和 Pod/Node 资源使用率指标，以监控底层资源和请求排队情况。
        - **服务层 (推理运行时):** 通过在 FastAPI 推理运行时中集成中间件，暴露自定义 Prometheus 指标，如 inference_request_total (总请求数), inference_request_latency_seconds (端到端请求延迟分布), model_load_duration_seconds (模型加载耗时，评估冷启动)。
        - **优化层 (批处理 Agent):** **正在为批处理 Agent 开发专属指标**，例如 batch_size_sum / batch_size_count (平均批大小), batch_processing_latency_seconds (批处理本身耗时), queue_wait_latency_seconds (请求在队列中的等待时间), slo_violation_total (SLO 违反次数统计)，为动态策略调优提供量化依据。
2. **动态批处理策略工程化实现（进行中，完成度 60%）**
    - **历史数据缓存与特征提取：** 在批处理 Agent 中，正在实现一个**简单的历史数据缓存模块**（例如，存储最近 N 次批处理的关键信息：时间戳、批大小、处理延迟、吞吐量估计、请求到达率估计）。计划使用滑动窗口等方法计算基本的统计特征。
    - **启发式调优逻辑开发：** 结合推理任务的 SLO 约束，**正在设计并实现两种基于规则或简单反馈的启发式调优逻辑**：
        - **逻辑一（平衡模式）：** 根据近期延迟和吞吐量反馈，尝试小幅调整 batch_size，观察性能变化趋势，以寻找较优的平衡点。
        - **逻辑二（SLO 优先模式）：** 当检测到 SLO 即将或已经违反时，优先减小 batch_size 或缩短 timeout 以降低延迟；在满足 SLO 的前提下，逐步增大 batch_size 或 timeout 以提升吞吐量。
3. **学术成果系统化梳理（进行中，完成度 20%）**
    - **论文结构规划：** 已初步规划论文的章节结构，主要包括：引言（研究背景、意义、国内外现状）、相关技术（Serverless、Knative、KServe、批处理技术）、系统设计（架构、核心组件）、批处理优化策略（算法设计与分析）、系统实现与实验评估、结论与未来工作展望。正在进行文献调研和相关技术背景部分的撰写。

二、存在的问题和拟解决方案

1. **问题：动态批处理策略的有效性与鲁棒性挑战。**
    - **潜在风险：** 当前设计的启发式动态批处理策略可能在某些复杂或剧烈变化的负载模式下表现不佳，例如，可能出现参数调整震荡、无法快速适应负载突变，或难以在延迟（SLO）和吞吐量之间达到预期平衡。简单规则可能无法覆盖所有场景。
    - **拟解决方案：**
        - **迭代优化与实验驱动：** 将重点放在构建灵活的实验框架上，允许快速测试和比较不同的启发式规则（包括不同的参数、不同的输入信号）。优先确保策略在几种典型的负载模式（如稳定并发、周期性波峰、突发请求）下，相比静态批处理或无批处理有明确改进。
        - **简化目标与度量：** 如果策略优化过于复杂，将优先确保满足核心目标，例如，对于 SLO 优先模式，将严格监控和惩罚 SLO 违规，即使牺牲部分吞吐量；对于性能优先模式，则关注平均/P95 延迟和吞吐量的综合提升。
        - **增加策略可配置性：** 允许通过配置（例如 ConfigMap 或 CRD 字段）调整策略的关键参数（如调整步长、观察窗口大小），而非完全硬编码，方便后期调优。
2. **问题：系统可观测性指标采集与解读的准确性问题。**
    - **潜在风险：** 在 Pod 内部精确测量请求处理各阶段的延迟（如队列等待、实际推理）可能存在技术挑战，测量本身可能引入开销或误差。错误或不精确的指标可能误导动态批处理策略的决策。
    - **拟解决方案：**
        - **关注核心与相对指标：** 优先确保最关键指标（如端到端延迟、批处理大小、队列长度、SLO 违反计数）的相对准确性。即使绝对值有误差，指标的变化趋势对于启发式调整通常更有意义。
        - **交叉验证：** 利用不同层级的指标进行交叉验证。例如，通过 Knative Queue Proxy 的指标（外部视角）与 Pod 内部 Agent 采集的指标（内部视角）进行对比，检查是否存在显著偏差。
3. **问题：集成测试与环境差异带来的复杂性。**
    - **潜在风险：** 将批处理 Agent、推理运行时、Knative 服务、自定义控制器（如果使用）、监控系统等多个组件集成在一起时，可能出现预料之外的交互问题或配置错误。在 WSL Kind 等本地环境测试的结果可能无法完全代表在更真实集群环境中的表现。
    - **拟解决方案：**
        - **关注相对性能提升：** 实验评估的重点将放在同一环境下，动态批处理策略相对于基线（无批处理、静态批处理）的性能提升比例，而非绝对性能数值，以减少环境差异的影响。在报告中明确说明测试环境及其局限性。
4. **问题：实验评估的充分性与论文撰写的深度。**
    - **潜在风险：** 有限的时间和计算资源可能导致无法进行足够广泛和深入的实验验证（例如，覆盖足够多的模型类型、负载强度、持续时间）。将工程实践有效转化为符合学术规范、论证充分的毕业论文也需要投入大量精力。
    - **拟解决方案：**
        - **聚焦核心场景：** 选取 1-2 个代表性的模型和几种关键负载模式进行深入测试和分析，确保核心结论的可靠性。
        - **边做边写：** 在进行系统实现和实验的同时，开始撰写论文的相关章节（如系统设计、实现细节、实验设置），避免最后阶段任务堆积。及时记录设计思路、遇到的问题和解决方案。
        - **明确贡献与局限：** 在论文中清晰地阐述研究的主要贡献（例如，特定场景下动态批处理 Agent 的设计与实现、启发式策略的有效性验证），同时诚实地指出研究的局限性（如测试环境、策略普适性）和未来可行的改进方向。
