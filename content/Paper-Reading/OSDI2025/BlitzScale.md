这是一篇来自于上交和华为云团队的，发表于 **OSDI '25** 的系统类论文，主要解决的是大语言模型（LLM）在模型即服务（MAAS）场景下的自动伸缩（Autoscaling）问题。

该论文针对现有 MAAS 系统（如 ServerlessLLM）在应对流量突发时扩容速度慢、导致SLO违约的问题，提出了两项核心技术革新：
1. 基于计算网络的快速数据平面（Fast Data Plane via Compute Network）：
    传统方法依赖 SSD 或主机内存缓存来加载模型参数，这受限于 SSD 带宽或主机内存容量（难以缓存所有模型）。BlitzScale 提出利用集群内闲置的高速 GPU 互联网络（RDMA/NVLink），通过**组播（Multicast）** 的方式在实例间传输参数。这一机制使得系统仅需在全局保留极少份数的模型副本即可实现快速分发，从而实现了 $O(1)$ 的主机缓存复杂度。
2. 细粒度层级协作的实时伸缩（Live Autoscaling with Fine-grained Abstraction）：
    现有的伸缩是“世界停止（stop-the-world）”式的，即新实例必须等所有参数加载完毕才能服务。BlitzScale 将伸缩粒度从“实例级”细化为“层级（Layer-level）”。新实例加载完部分层后，即可通过与过载的旧实例协作开始分担计算任务。为此，作者设计了 ZigZag 调度算法来动态平衡新旧实例间的负载，最大化吞吐量。

## 设计的出发点

### 1. 现有技术瓶颈

在 MAAS 场景下，流量具有极强的突发性。以论文引用的真实负载 BurstGPT 为例，推理请求量可能在 2 秒内激增 5 倍。由于 LLM 推理对显存（特别是 KVCache）的巨大需求，系统无法预先过度配置资源，必须依赖自动伸缩（Autoscaling）。

然而，现有的伸缩机制面临着物理带宽的硬约束，导致严重的 SLO 违约。

**挑战一：SSD 带宽无法满足紧迫的 SLO**

用户对交互式应用（如聊天机器人）的延迟极其敏感，通常要求响应时间在 1 秒以内（TTFT < 1s）。对于像 Qwen2.5-72B 这样的大模型，要满足这一 SLO，留给模型加载（Data Plane）的时间窗口仅有不到 500ms 。
![](private/快手项目/papers/1216/assets/Pasted%20image%2020251216195019.png)
- **带宽需求推算**：在 500ms 内加载 72B 模型的参数，意味着需要高达 **576 Gbps** 的单 GPU 传输带宽 。
- **现实差距**：现有的商用 GPU 服务器 SSD 带宽通常仅为 **2-10 Gbps** 4。如图 3(a)-(d) 所示，仅依赖 SSD 加载会导致极高的 SLO 违约率（超过 60%） 。

**挑战二：主机缓存（Host Caching）的不可持续性**

目前的 SOTA 系统（如 ServerlessLLM）试图通过将模型缓存在 CPU 主机内存中，利用较快的 PCIe 总线（约 256 Gbps）来缓解 SSD 瓶颈。然而，这种方案在多租户环境下存在根本性的扩展性问题：
![](private/快手项目/papers/1216/assets/Pasted%20image%2020251216195024.png)
- **缓存容量限制**：MAAS 平台通常托管数百甚至数千个模型（及其微调变体）。主机内存有限，无法缓存所有模型。
- **高缓存未命中率**：论文实测显示，在真实负载下，ServerlessLLM 的缓存命中率仅为 **40%-75%**。如图 4 所示，随着时间推移和请求波动，缓存未命中（Cache Miss）频繁发生。一旦未命中，系统就会回退到缓慢的 SSD 加载，导致性能骤降。
    
### 2. 被闲置的计算网络

鉴于存储介质（SSD）太慢且主机内存（DRAM）容量不足，论文将目光转向了数据中心内另一个关键资源——**计算网络**。

**优化点一：网络带宽的代际优势**

现代 GPU 集群通常配备两层网络：
1. **Scale-up 网络**：如 NVLink，提供超高速互联（1.6 Tbps - 16 Tbps），用于单机多卡间的通信。
2. **Scale-out 网络**：如 RDMA，提供节点间的高速通信（100-400 Gbps） 。
这两种网络的带宽均远超 SSD，且 Scale-up 网络甚至快于 PCIe。如果能从其他已加载模型的实例（Peer GPU）而非 SSD 拉取参数，加载速度将获得数量级的提升。

**优化点二：推理时的网络利用率低**

一个疑问是：推理过程中是否已经占满了网络带宽？
![](private/快手项目/papers/1216/assets/Pasted%20image%2020251216195029.png)
现有的 LLM 服务常采用 PD 分离（Prefill-Decode Disaggregation）架构，确实涉及 KVCache 的传输。然而，论文通过测试（如图 3(e)-(f)）发现了一个现状：
- 即便是网络密集型的 PD 分离架构，在峰值负载下，计算网络依然有超过 **40%** 的带宽处于闲置状态。
- 在许多常规负载下，网络利用率甚至不足 10% 。
    
### 3. 设计思路

基于上述分析，论文确立了核心的设计思路：**与其依赖命中率不稳定的主机缓存，不如利用集群内闲置且高速的计算网络，在实例间直接进行模型参数的组播（Multicast）。**

由此，BlitzScale 提出了两个核心目标来解决上述挑战：
1. **利用计算网络实现 $O(1)$ 缓存**：通过网络从任意持有模型副本的节点（GPU 或 CPU）拉取参数。理论上，只要集群内有 _一份_ 模型副本，所有节点都能以接近网络带宽的速度加载，从而彻底消除对单机缓存命中率的依赖。
2. **打破“全停（Stop-the-world）”模式**：即使网络再快，对于超大模型仍有传输延迟。既然参数是分层传输的，为何不让计算也分层进行？这引出了**实时伸缩（Live Autoscaling）** 的概念，即在传输的同时开始计算 。

## 整体架构

结合论文中的 **Figure 6**，我们可以将整个系统划分为控制平面和数据平面的协同。

BlitzScale 的架构引入了四个关键的新模块，与传统的模型服务组件协同工作：

1. **全局参数管理器 (Global Parameter Manager / Pool)**
    这是一个中心化的元数据管理服务。它不直接存储海量的模型参数数据，而是维护一张**参数位置映射表（Location Mapping）**。它记录了模型参数当前分布在哪些位置，包括正在提供服务的 GPU 显存（Deployed instances）以及各计算节点的 CPU 主机内存（Local model cache）。当需要扩容时，它能迅速向调度器提供所有可用的“源端（Sources）”，从而利用 RDMA 或 NVLink 从多个源头并行拉取数据，而非仅依赖单一存储源。
2. **负载监控与触发器 (Load Monitor & Trigger)**
    实时监控各模型服务的负载指标（如 Token 生成速率、KVCache 占用率）。采用基于阈值的策略。当监控指标突破预设的上限（Upper Bound）时，触发扩容信号；反之则触发缩容。这一部分是自动伸缩的决策大脑，决定“何时伸缩”以及“伸缩多少实例”。
3. **伸缩规划器 (Scale Planner)**
    这是 BlitzScale 的核心控制组件之一。它负责在接收到扩容指令后，动态生成**数据传输拓扑图（Multicast Plan）**。这一部分需要在异构网络环境下（混合 RDMA 和 NVLink），针对动态变化的源端和目的端，生成一个无干扰且带宽利用率最优的传输路径 。一个具体的传输计划，指示哪些节点应该向哪些节点转发参数（例如构建转发链 `Source -> Target1 -> Target2`）。
4. **实时执行调度器 (Live Execution Scheduler)**
    负责在伸缩过程中精细化地分配推理请求。它打破了“stop-the-world”模式。在参数加载的中间状态（例如新实例只加载了前 50% 的层），调度器就会介入，将请求的对应层级计算（前 50% 层）卸载到新实例上执行，而剩余层级可能仍由旧实例处理或等待加载。这里运行着论文提出的 **ZigZag 调度算法**，确保新旧实例间的流水线协作不会因为负载不均导致流水线气泡或额外的排队延迟。
5. **模型执行器 (Model Executor)**
    位于每个 GPU 节点上的执行引擎。基于 FlashInfer 等高性能算子库构建，支持细粒度的层级（Layer-wise）执行控制，以响应实时调度器的指令。

结合架构图，一次完整的自动伸缩流程如下：

1. **触发 (Trigger)**：`Load Monitor` 检测到某模型（例如 Llama-3-8B）负载过高，向系统发出扩容请求。
2. **规划 (Plan)**：
    - `Scale Planner` 介入，查询 `Global Parameter Manager`。
    - 它发现该模型的参数在节点 A 的 GPU 上有一份副本，在节点 B 的 CPU 缓存中也有一份。
    - Planner 根据当前网络拓扑，计算出一条最优的组播路径（例如：节点 A 通过 RDMA 推送给新节点 C，同时节点 B 辅助推送），并确保该路径不会与当前的推理流量（如 KVCache 传输）发生网络竞争。
3. **传输与执行 (Transfer & Execute)**：
    - 新节点 C 开始接收参数层。不同于等待全部加载完成，`Live Execution Scheduler` 立即接管流量导向。
    - 一旦 C 节点加载完Layer 1，调度器就开始将部分请求的 Layer 1 计算任务分发给 C。
    - 随着 Layer 2, Layer 3... 陆续到达，C 节点承担的计算量逐层增加，直到全量参数加载完毕，C 节点完全独立承担服务。

BlitzScale 的架构本质上是一个**以网络为中心的分布式流处理系统**。它将“模型加载”视为一个可被精细调度的数据流，将“模型推理”视为一个可被拆解的计算流，并通过全局视角的规划器和调度器，实现了这两股流在时间和空间上的共同优化，从而达成了 **Fast（高速组播）** 和 **Live（实时协作）** 的设计目标。


## 核心设计

这里，我们将核心关注点从“系统做了什么”下沉到“系统是如何做到”的，特别是针对 **C#1（在线无干扰伸缩规划）** 和 **C#2（实时流水线调度）** 这两个论文提到的核心挑战。

### 1. 挑战一：在线网络组播规划的复杂性与干扰

尽管利用计算网络进行参数传输在理论上可行，但在实际的生产级集群中，拓扑结构的异构性（NVLink 与 RDMA 并存）以及现有推理流量的存在，使得构建高效的传输计划变得极为困难。

一方面，集群网络通常呈现 [Leaf-Spine 架构](https://zhuanlan.zhihu.com/p/588523823)，且节点内部存在极高带宽的 Scale-up 网络（如 NVLink，1.6-3.6 Tbps）。为了解决在异构网络上生成最优组播树这一 NP-hard 问题，BlitzScale 采用了分层抽象策略：

首先，利用 NVLink 的广播特性，将同一机器内的多个 GPU 视为一个逻辑上的“实例组”。由于 NVLink 带宽远超 RDMA，组内传输延迟可忽略不计。这一抽象极大地降低了拓扑图的节点数量，将问题简化为跨节点的 RDMA 传输规划。

在 Scale-out 层面，核心矛盾在于避免伸缩流量与服务流量（特别是 PD 分离架构下的 KVCache 传输）发生带宽竞争。

论文通过分析 RDMA 网络的全双工特性发现，入站（Incast）与出站（Outcast）流量互不干扰 。据此，规划器采用了一种服务感知（Serving-guided）的贪婪算法来构建传输路径：

1. **干扰剔除**：如果某条链路方向上存在正在进行的 KVCache 传输（例如 Prefill 实例向 Decode 实例发送数据），规划器会禁止在该方向上调度模型参数传输。
2. **串行转发链**：针对剩余的可用链路，算法构建 $S \to T_1 \to T_2 \dots \to T_n$ 的串行链结构。
    - _设计原理_：对于带宽密集型任务，串行链的总传输时间取决于最慢链路的带宽，而与链长无关。每个节点在接收数据的同时也充当转发者，实现了流水线式的带宽利用。
    - _多链并行_：为了适配 Leaf-Spine 结构并进一步规避局部拥塞，算法会构建多条并行的串行链，优先选择高带宽路径。

### 2. 挑战二：实时伸缩中的执行调度（ZigZag Scheduling）

解决了数据传输问题后，下一个瓶颈是“计算能力的线性增长”与“请求到达的离散性”之间的错配。

在实时伸缩过程中，新实例（Target）的计算能力是随着参数层的加载逐层递增的。

若采用简单的 **尽力而为（Best-effort）** 策略——即新实例每加载完一层就立即分担该层的计算——会导致严重的负载不均衡。

我们假设一个场景：模型有 7 层，加载一层的时间足够执行 6 层的计算。

那么在初期，新实例仅加载了少数层（如 1 层），此时它能分担的计算极少。大部分负载仍积压在旧实例（Source）上，导致请求在旧实例排队超时，即便新实例处于空闲等待状态。

为了解决上述问题，论文提出了 ZigZag 调度算法。其核心思想是用时间换空间：通过在旧实例上策略性地“延迟”部分请求的执行，为新实例争取加载更多层的时间窗口，从而在后续的时间步中以更优的配比进行卸载。

该算法在逻辑上包含两个步骤：

1. 基于整数线性规划（ILP）的流水线配置：
    对于每一批请求，算法试图寻找一个分割点 $(S_i, T_i)$，其中 $S_i$ 是旧实例执行的层数，$T_i$ 是新实例执行的层数。目标是最小化平均延迟，约束条件包括流水线依赖（旧实例处理完前 $S_i$ 层后，新实例必须已准备好处理后续层）和加载限制（新实例必须已加载完对应的 $T_i$ 层参数）。
2. 免求解器的启发式实现：
    考虑到在线求解 ILP 可能引入额外延迟，BlitzScale 实现了一种比较高效的启发式逻辑：
    - 新实例维护一个优先队列，优先处理那些“下一层参数已加载”的请求。
    - 旧实例仅在自身完全空闲时才从新实例拉取任务。
    - 这种机制自然形成了一种“ZigZag”式的交替执行模式。随着新实例加载层数的增加，请求在两端流转的比例动态调整，最大化了系统的整体吞吐量，消除了流水线气泡。

### 3. LLM 特化：针对 PD 分离架构的优化

针对大语言模型特有的 Prefill-Decode (PD) 分离架构，BlitzScale 进行了特定的逻辑适配。

在 PD 架构中，Decode 实例的伸缩不仅涉及参数加载，还面临 KVCache 迁移带来的入站带宽竞争，这使得直接对 Decode 实例进行实时伸缩变得不可行 。

论文观察到，Decode 实例的需求往往滞后于 Prefill 实例。当系统检测到需要扩容 Prefill 实例时，可以推断出随后必然需要更多的 Decode 资源。

因此，BlitzScale 采取了一种预伸缩策略：在扩容 Prefill 实例的同时，利用剩余带宽同步启动 Decode 实例的扩容。由于此时 Decode 阶段尚未成为瓶颈，这种操作几乎没有边际成本，却能有效掩盖后续 Decode 实例的启动延迟。
